# 天星宗时间线规划草案（lab）

日期：2026-06-28

## 核心结论

`推命` 不能由裂缝、野外、闭关、斗法这些模块各自“临发前补一下”。

天星不是独立玩法，它会横切并改写四条原有主链：

- `闭关`
- `斗法`
- `探索`（`野外历练` + `探寻裂缝`）
- `炼制`

原因：

- `推命` 覆盖的是接下来 `8 小时` 的路线承诺。
- 一旦押了某一路，再去做别的路，就有 `推命落空 -> 逆命劫 +1` 的风险。
- 所以它必须先有一条时间线，再决定是否发。

## 正确层级

### 第一层：时间线规划

负责回答：

1. 今日是否已经定命
2. 未来 8 小时主路线是什么
3. 接下来会不会混入别的高优先级动作
4. 当前是否值得押 `探索 / 闭关 / 炼制 / 斗法`

只有这一层，才有资格决定：

- 要不要 `推命`
- 推哪一路
- 何时推

### 第二层：路线前置

负责回答：

1. 这个动作能不能直接发
2. 是否缺 `定命`
3. 是否缺对应 `改命`
4. 当前是否被别路推命阻断

这一层不决定 `推命`，只消费时间线规划的结果。

### 第三层：执行层

负责：

- 真正发送命令
- 走全局发送队列
- 受安全锁/审计/补发节制

这里要特别注意：

- 全局发送锁只能保证“谁先拿到发送权，谁先发出去”
- 但它**不能**替你决定“推命应不应该先于改命存在”
- 如果 `run_tianxing_scheduler()` 和 `野外/裂缝前置` 是两个独立来源，即使单次发送串行，也仍然可能出现结构性竞态：
  - scheduler 规划了一个 `推命 闭关`
  - 探索模块前置又想补一个 `改命 探索`
  - 两边分别在不同 tick 竞争发送锁
  - 结果不一定符合时间线语义

所以顺序正确不能只靠 runtime 锁，必须由时间线规划层先把“本阶段允许什么战略动作”定下来。

## 探索路线建议时间线

### 每日启动

1. 查盘 / 观命
2. 若未定命，按策略定命

### 探索窗口规划

先汇总未来探索动作：

- 野外历练的预期触发时间
- 探寻裂缝的预期触发时间
- 其他探索类动作（后续若纳入）

再判断：

- 接下来 8 小时内，是否大概率以探索为主
- 是否会插入闭关/炼制/斗法等主路线动作

只有“探索确实是主路线”时，才允许：

- `.推命 探索`

### 探索动作前

模块前置只做：

1. 检查异路推命冲突
2. 检查是否需要 `定命`
3. 检查是否需要 `改命 探索`

不再自行决定 `推命`

## 下一步建议

继续完善 lab 审计层，统一由下游模块提交路线窗口，例如：

```python
build_tianxing_timeline_plan(
    now=now,
    horizon_hours=8,
    windows=[...],
)
```

输出应至少包含：

- `dominant_route`
- `should_predict`
- `predict_route`
- `predict_reason`
- `blocked_by_conflict`
- `route_windows`

然后由独立 scheduler 决定是否发送：

- `.推命 探索`
- `.推命 闭关`
- `.推命 炼制`
- `.推命 斗法`

下游模块只消费已确认的 `release_downstream`，不得各自补 `推命`。
