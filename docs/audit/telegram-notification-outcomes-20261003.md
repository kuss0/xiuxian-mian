# 通知回执分类修正

## 原因与边界

真实采样已开始，13:17 读到两条 Bot confirmed 回执：首条正常摘要、第二条原有贵重物品第 3/3 次提醒（一次管理员提及），不是新增告警风暴。没有相同 payload 的重复确认；样本太少，不报告全天降噪率。

进一步审查发现 `requests` 层将超时、代理/连接异常和非正常 HTTP 响应转换为 `(False, error_text)`；上一版采样把所有正常返回的 False 记成 unconfirmed，只有抛到异步层的超时才记 unknown。同一网络故障因此有不同口径。此缺陷由隔离测试复现，不冒称自然窗口已出现过该故障。

## 修改

- `audit_delivery.bot_delivery_outcome` 仅分类统计：明确成功是 confirmed；本地明确未发送条件或与 HTTP 状态一致的 Bot JSON 4xx 拒绝是 unconfirmed；其余均保守归 unknown。
- 正常返回的网络超时、连接/代理错误、5xx、非 JSON、矛盾状态码及异常深层 JSON 均不再伪装成明确拒绝。
- 分类只在 `_note_log_delivery` 的异常隔离层内运行，且回执开关关闭时不运行。分类自身异常不会改变主/副通知渠道的返回值、退避或回退。
- 不记录错误正文、URL 或凭据，不追溯重写旧回执。
- **本次不修改 Bot 超时后账号回退**，一次调用内的潜在双发仍属 TG-06；不能将分类修正视为投递安全债务全部销号。结构化摘要仍关闭。

## 验证

- 最终定向：`265 passed, 298 subtests passed in 7.64s`，覆盖摘要、通知控制、回执报表、关停、原有发送超时/回包观察。
- 用 requests.ReadTimeout 走真实 Bot helper 的模拟链路，验证正常返回 False 仍得到 unknown；明确 403/429、异常 JSON 及分类失败不影响退避均已覆盖。
- 全仓 Ruff、compileall、diff 检查通过。该补丁未重新跑全仓 1.5 万项，不将之前全仓结果当成本次结果。
- 生产预检：health observer 正常；待处理回包为空；WA 裂缝 17:59:27，尚未进入准备窗口；独立 listener 仍按原设定 inactive。
