当前 `origin/main` 最新提交为 `f5817330`，其洞府 MiniApp 分段
`start/details/section` 适配已由本地主线 `2bbae914` 吸收。继续比较后，最明确的

再单独评审生产接入。

## 南宫阙协议差异

- 入口 token：`nqb_*`；本地协议层可识别，生产运行层仍只启动青原子 `qyz_*`。
- API：`/api/miniapp/xianxia-nangongque-boss/start`、`state`、`input`、`claim`。
- `start`：选择 `playerId` 并建立房间/会话，属于非幂等动作，传输状态未知时不得重放。
- `state`：读取房间、Boss、玩家、危险区、机制和结算，可作为只读校准入口。
- `input`：连续提交移动、闪避、机制或攻击，必须受全局 MiniApp 限流和单房间节拍控制。
- `claim`：领取结算，需以服务端 `claimed` 状态幂等校准，不能仅凭本地成功返回重复调用。

上游参考节拍为输入约 `0.46s`、状态约 `1.4s`、运行摘要约 `4s`。这些只能作为
Lab 样本，不能绕过本地 MiniApp 全局 `90 次/分钟` 上限，也不能与四身份并发预算
直接叠加。

## 本地接入 Gate

1. Gate A：只加入 `nqb_*` 入口识别、脱敏摘要和广播/结算文案解析，不发送 HTTP。
2. Gate B：建立独立 adapter 与 `start/state/input/claim` 请求结构，使用录制回包离线回放。
3. Gate C：实现单身份、单房间状态机；`start/input/claim` 禁止传输层自动重试，未知状态只用 `state` 校准。
4. Gate D：加入危险区判定、移动/闪避/机制/攻击决策和总请求预算测试，验证不会超过 90 次/分钟。
5. Gate E：真实单身份 Lab canary；确认结算、奖励领取、掉线恢复和日志脱敏后，另审多身份并行。
