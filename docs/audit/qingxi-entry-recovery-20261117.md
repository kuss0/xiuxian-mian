# 青溪入坊失败与天星取消恢复

## 已确认的问题

- 青溪 worker 在 `open_page()` 返回前入坊失败，主流程拿不到页面对象，因而跳过现场快照和收尾；真实加载错误也被固定错误码覆盖。
- 旧收尾忽略 `refresh()` 返回 `null`，仅凭旧快照判断服务端核对成功。
- `held` 被调度永久跳过；河岸钓获也不会唤醒冻结记录的只读复核。
- 吧唧浏览器磁盘日志残留 `field-cast:begin:1794849744016`；上一轮真实 ACK 和后续完成回执已确认该上传。旧 worker 使用终止信号退出 Chromium，磁盘记录可能落后于内存状态。
- 天星外层取消一律标记发送未知，未采用发送层的“RPC 前取消、确定未发出”证据。
- 部署后观察到玄骨准备阶段实际耗时超过三分钟：加入和分工均已确认，但进入命令排队后被旧截止时间拦截，记录为确定未发送。过期取消又把这条未发送记录当作未知入场，持续占用五个身份。
- 玄骨确认旧房取消后，日计划仍保留 `attempt_day` 和周次数预留，导致未入场也阻断当日后续安排。
- 本轮上游在采集时发生位移，`gather-cancel` 已成功确认，但本地将这次已取消的采集永久视为玩法未知。

## 修补边界

- 页面创建与入坊分开，入坊错误保留原文；停止或排空失败时仍尽力保存现场。
- 最终核对要求新的成功任务状态回执、正确身份、完整状态结构，以及内存和磁盘均无未决操作。刷新失败、旧缓存和身份不符均不能放行。
- 正常停稳的已确认战斗若仅最终状态刷新失败，后续新的任务状态和飞行关闭证明可解除等待；未决请求、未知战斗结算及仍在进行的副本继续保留围栏。
- 冻结记录每半小时只读复核；钓获可提前唤醒只读复核。未决写入和无进展冻结不因刷新成功直接解除。
- Chromium 正常关闭并等待退出。旧磁盘施法记录只在同身份的成功结果中找到同操作 ID、且 ACK 晚于该记录时清除；不重放施法或战斗操作。
- 天星仅凭本次发送期间的新鲜确定未发出证据恢复待发；RPC 后取消、旧证据及未知结果继续保留围栏。
- 玄骨准备预算覆盖四次加入、五次分工及进入的串行排队，截止时间受原房间有效期约束。完整分工回执可核对尚未尝试进入的准备超时；确定未发送的入场记录允许过期取消，等待队长真实回包后才释放占用。
- 每次玄骨预留与花名册共用唯一编号；仅本次原房的取消或无队伍终回包、且完全没有已发出或未知入场、轮次、领奖证据时，释放对应预留。保留取消证明并延迟五分钟重排，历史回包不能释放新房次数。未知入场仍占用次数；每日领奖和每周最多三次限制保留。
- 采集位移只在最后一条采集操作为成功取消、新任务状态核对通过、内存与磁盘未决均为空、战斗关闭及服务端飞行关闭后恢复。未确认取消、后续又开始采集或未知战斗均不解除围栏。
