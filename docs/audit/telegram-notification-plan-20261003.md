## 1. 目标

TG 用于提醒需要关注的变化，不作为逐条搬运运行日志的终端。

- 只有紧急风险、时效操作和明确重要结果允许单独推送。
- 普通异常、预期等待、日常收获按事件和批次合并，避免每身份、每步骤各发一次。
- 固定分类、顺序和句式，让用户先看结论、影响和必要操作，再按需展开细节。
- 降低通知数量，不降低异常检测能力；不能把错误隐藏、把无回包改称成功，或靠延长业务 CD 降噪。

## 2. 已核实的问题

| 现状 | 证据 | 影响 |
| --- | --- | --- |
| 上次只改展示 | `docs/audit/telegram-notification-compact-20261002.md` 明确未改优先级和间隔 | 折叠减少高度，不减少消息数量 |
| 大量优先级由文案猜测 | 当前 `model/` 有 496 个直接 `send_audit_log` 调用点，其中 388 个未传 priority | 同类事件随措辞改变分级；含“失败/超时/不足”等即进入实时中优先级 |
| normal 也是实时推送 | `runtime._AUDIT_PRIORITY_ALIASES` 把 normal 映射为 medium；30 个调用点显式传 normal | “普通结果”容易被误以为已汇总，实际仍单发 |
| 合并键是整段文案 | `_queue_low_priority_audit` 用含身份前缀、经过裁剪的 plain_body 作键 | 身份、时间、奖励数量变化就分裂；裁剪后相同也可能错误合并 |
| 摘要按重复次数排序 | `_format_low_priority_audit_summary` 按 count、seq 排序 | 高频琐事占前列，不按重要性、模块或处理状态组织 |
| 仅低优先级进入合并 | `send_audit_log` 的 medium/high 直接发送 | 同一故障在多个身份、多个步骤反复推送 |
| 不止一个发送入口 | runtime、红包第二渠道、watchdog、独立日报工具各有发送路径 | 只改 runtime 无法覆盖全部通知；也不能让独立 watchdog 依赖主进程存活 |

配置代码默认低优先级汇总间隔为 600 秒、最多 20 类；仓库 `.env` 未覆盖这两个值，进程级实际配置仍需在实施基线中核实。

只读抽样：最近 24 小时主服务 journal 共 1582 条，其中启动/恢复匹配 39 条、MiniApp 失败匹配 1 条、日报匹配 5 条。它包含非推送控制台记录，不是 TG 实际送达量，不能据此宣称当前群消息数或降噪比例。实施前补实际通知发送/送达基线；不为采样复用正在运行的 Telegram session，不重发历史业务。

## 3. 默认通知策略

优先级和是否 @ 分开判断。重要成果可以单发，但不等于需要叫管理员。

| 类别 | 例子 | 默认行为 |
| --- | --- | --- |
| P0 紧急处置 | 已确认重复消费、身份误操作、意外全局停机、封禁、即将错过的必要人工操作 | 首次立即单发；只有确需人工介入才 @。相同未变化事件不连发，未恢复每 60 分钟最多补提醒一次；风险升级或操作截止临近可立即升级 |
| P1 重要事件 | Boss 有时效的入场提醒、整场个人结算、指定稀有物资、重要任务完成 | 按同一事件/批次合并一条；成果默认不 @。按钮或有效操作窗口不能延迟到常规汇总 |
| P2 普通摘要 | 日常修炼/出窍/收割完成、已自动恢复的短暂异常、非紧急但持续的模块问题 | 每 30 分钟至多一条综合摘要，无变化不发，不 @；首屏仅列值得关注的变化 |
| P3 过程记录 | 开始执行、排队、查状态、等待 CD、预期安全锁拦截、无鱼竿等已知条件跳过 | 只留后台/本地，不逐条进 TG；需要时在摘要中计为等待或跳过，不包装成失败 |

这些是待实施默认值，不是当前已生效配置。

例外与边界：

- 红包保持此前明确要求的成功卡校验、金额门槛、三次提醒、双渠道和直达链接，作为有界时效白名单；不把三次有意提醒误判为重复事故。
- 指定贵重奖励已有重复提醒策略先列清单核对，不暗中取消，也不把所有奖励自动升级。
- 资源不足不一律降级：预期不足是等待；例如已经开启补煞却一直未执行，属于真实业务故障，须根据影响升级。
- 安全锁“正确等待”不单发；链路过期、锁长期不释放或本应执行却漏执行，仍按真实异常升级。
- 超时但结果未知不是成功，也不等于已经消费；通知只能描述原状态，不修改状态机结论。
- 用户主动查询、设置保存反馈、交互按钮确认不是后台噪音，保留及时响应。
- watchdog 紧急通知不受普通摘要预算阻塞；保留独立发送能力，不绑定主服务队列。

## 4. 合并单位与生命周期

### 4.1 使用业务键，不用整段中文当键

在原 `send_audit_log` 入口上逐步补充可选结构化信息：事件类型、模块、身份 ID、事件/操作/批次 ID、原因码、状态及必要的截止时间。尽量直接使用现有字段，不新增一套业务状态机。

- 同一操作：按稳定身份 ID + 模块 + operation/event ID 识别，用户名只用于展示，改名不破坏去重。
- 同一批次：使用现有 batch/event ID，并在批次启动时固定参与身份集合，不能以运行过程中不断变化的启用集合推导“全员完成”。
- 同一公共故障：仅有确凿共享原因时，按依赖作用域及原因码聚合受影响身份，例如同一登录账号失效。不要把不同凭证、不同入口的独立故障合成一个已恢复事故。
- 跨群广播：以业务事件身份去重；缺少全局事件 ID 时按已有可靠证据关联，不凭相似文案吞掉另一场事件。
- 不用正则简单删除所有时间、数字和用户名后合并，防止吞掉不同奖励、不同目标或不同回包。
- 尚未迁移的调用走现有兼容路径，并记入覆盖清单；禁止一次性把全部未知 high/medium 降成摘要。

### 4.2 一件事只占一个通知生命周期

同一事件记录首次发生、最近发生、影响身份、次数、当前状态和上次已推送状态。

- 首次达到阈值才推送；重复只更新计数和影响范围。
- 严重度提升、影响显著扩大或必须人工处理时立即更新；普通重复进入摘要。
- 恢复必须来自真实成功/状态校准证据，不能由“最近没有报错”推断。
- 原告警发过才补恢复信息，通常并入下一条摘要；未曾通知的瞬时抖动不再单发“恢复”。
- 不跨事件错误归并“失败 -> 成功”。失败后另一次操作成功，不自动核销上一笔未知消费。
- 紧急首报不等待“聚齐全部身份”；后续影响范围再合并。首版不要求原消息编辑，避免为降噪先扩展整套消息回执接口。

### 4.3 多身份、多步骤先收口再汇报

- 闭关、元婴、钓鱼、观星台等日常结果按模块批次或摘要窗口合并；不逐角色播启动、读取、领取、下一次时间。
- 钓鱼、天机命脉等既有日结只保留一次最终成果；未齐时按模块截止条件报告“部分完成”，不一直等坏身份，也不伪称全员完成。
- Boss 同一场的脚本个人结算合并；全服胜利不能替代本方结算。确有人工时效的开场通知和最终结算允许各一条。
- 跳过、失败、未确认、完成分开计数；“无鱼竿”不计作成功完成或公共入口故障。
- 收获只累计带业务来源 ID 的确认增量，不能把重复日志、群广播和日报再次累加。优先复用现有成果账本，不另建奖励账本。

## 5. 展示规范

只保留固定消息类型：`需处理`、`重要结果`、`运行摘要`、`今日收获`。时间窗使用 UTC+8，身份显示当前可读名称。

紧急消息首屏格式：

```text
[需处理] 模块 | 影响身份
问题：发生了什么，对业务有什么影响
已处理：脚本已经采取的措施
需要你：确实必要且可执行的操作
来源：已有真实消息的直达链接
```

常规摘要结构：待处理异常 -> 已恢复变化 -> 已确认收获。每模块一行，受影响身份和过程放折叠明细，不再按日志次数抢占首位；没有内容的分区不显示。

- 常规首屏目标 6-8 行，重要告警首屏 4-6 行；全条含折叠细节控制在 3500 UTF-16 单元以内。
- 每条普通摘要最多 20 行折叠明细，超出显示省略计数并引导到已有后台日志，不拆成一串续篇刷群。
- 每条先写结论，再写影响和下一步；不要以 `failed / blocked / phase / session / msg_id` 堆砌标题。
- 原因码、消息 ID、校准时间等放明细；不得显示 cookie、token、initData、原始鉴权链接。
- 保留已有 Telegram 原生折叠、HTML 转义和 UTF-16 裁剪工具；只允许明确的管理员提醒产生 mention，普通用户名仍防自动 @。
- 不生成不存在的消息/后台跳转地址；有有效来源才展示链接。
- 默认不报“0 条记录”“没有新增物资”“一切正常”等空摘要。用户主动查询状态不受此限制。

## 6. 实现收敛与投递安全

- 保留 `send_audit_log` 作为业务入口、`audit_messages.py` 作为展示工具；新增最小可测策略模块，不逐业务再发明限频字典。
- 已迁移事件只经过一个通知决策器，不同时进入旧低优先级桶和新摘要器。暂时兼容的旧路径在覆盖完成后删除，不长期双轨常驻。
- 通知聚合与必要去重游标支持有界持久化，不能重启清空后把旧告警重新刷一轮，也不能因持久化故障阻断游戏回包处理。优先复用现有 SQLite 工具；独立通知命名空间，不回写业务快照。
- 聚合窗口、已送达记录、已恢复事件分别设清理策略；建议已送达/已恢复保留 7 天，活动记录按事件期限处理并设置容量上限。到限时普通明细计数压缩，不能静默丢紧急待投递项；存储失效由独立监控报警。
- 发送明确成功后才记已送达；失败保留待投递状态，按 Telegram retry_after 有界退避。过期时效通知不在网络恢复后集中补刷。
- 通知自身异常只记本地诊断或由独立监控提醒，不能递归产生更多通知。
- 现有 `_send_log_group_message` 在 Bot 超时后会尝试账号回退，可能存在“Bot 实际已送达但回执未知”的重复风险。未证实本轮真实双发；作为独立投递债务测试，不用合并文案掩盖，也不借机修改游戏发送层。
- watchdog 可共享纯分级/文案规范，但继续独立运行、独立紧急出站；独立日报先统一格式和事件键，不强制汇入主进程。
- 首版不加新 MQ、外部服务或通用事件框架，不设计复杂订阅中心。

## 8. 测试与上线门槛

- 单测：身份改名、相同文案不同事件、不同文案相同事件、跨身份共享故障、同事件晚到/乱序、风险升级/真实恢复、重复收益、窗口边界、时效过期。
- 可靠性：并发入桶与发送、失败回存、重启恢复、容量上限、持续故障、TG 429、发送结果未知、Bot/账号切换；通知故障不改变业务 state 或堵住回包。
- 展示：长中文/表情/链接/HTML/折叠、首屏有真实处置要求、无意外 mention、无凭据泄漏、全条不超长。
- 端到端回放：多身份整批成功、缺鱼竿、一个身份超时、公共入口失效、阴罗补煞未执行、天星等待与真实卡死、Boss 个人失败/全服成功、红包双渠道白名单、watchdog 主服务离线场景。
- 回放目标：可合并的日常/重复非紧急推送条数比基线减少至少 70%；普通摘要不超过每小时 2 条；新增 P0 无主动聚合延迟、无遗漏。时效白名单和独立紧急事件不为了凑比例被压制。
- 数量降低不能作为唯一验收：关键问题仍需可见，重复/抑制/待投递计数可查，没有错误“恢复”和重复奖励。
- 有限上线后观察至少 24 小时和一个完整自然日结；缺少关键自然样本就保留该验收项，不造业务消息补样。
- 回退只切回通知路由或回退相应代码；已送达游标保留，不重放旧摘要，不回滚游戏数据。

本计划不代表实施、上线或债务销号。后续每项附测试、通知前后对照、自然消息证据和提交记录。
